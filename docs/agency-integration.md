# سازوکار اتصال اداره‌ها و سازمان‌ها به هوش هرمز

## هدف
یک مسیر یکپارچه برای ثبت، ارجاع، پیگیری و بستن درخواست‌ها؛ به‌گونه‌ای که اداره بتواند ابتدا بدون تغییر نرم‌افزار داخلی خود شروع کند و بعداً در صورت آمادگی به API متصل شود. این سند طرح فنی است؛ تا زمان پیاده‌سازی و تأیید، هیچ اداره‌ای متصل یا تأییدشده محسوب نمی‌شود.

## سه روش اتصال

### روش ۱ ـ پنل وب مستقل (شروع آسان)
کارمند مجاز با حساب سازمانی وارد پنل می‌شود، درخواست‌های ارجاع‌شده به سازمان را می‌بیند، مسئول تعیین می‌کند و وضعیت/پاسخ را ثبت می‌کند. این روش برای اداره‌ای مناسب است که تیم فنی یا API ندارد. ورود باید با احراز هویت و نقش‌های محدود انجام شود؛ لینک عمومی به‌تنهایی دسترسی ایجاد نمی‌کند.

### روش ۲ ـ API امن (برای سامانه‌های دارای تیم فنی)
سامانه داخلی اداره از طریق HTTPS با API هرمز تبادل اطلاعات می‌کند. هر سازمان کلید مستقل و قابل ابطال، مجوزهای محدود، سهمیه درخواست و فهرست IP مجاز در صورت امکان دارد. کلیدها فقط در سرور نگهداری می‌شوند و هرگز در مرورگر، کد صفحه یا پیام‌رسان قرار نمی‌گیرند.

### روش ۳ ـ Webhook (اعلان تغییرات)
هرگاه وضعیت پرونده تغییر کند، هرمز یک اعلان امضاشده به نشانی ثبت‌شده سازمان می‌فرستد. گیرنده امضا و زمان را بررسی می‌کند و برای جلوگیری از پردازش دوباره، شناسه رویداد را ثبت می‌کند. در صورت خطا، تلاش مجدد و گزارش خطا لازم است.

## چرخه استاندارد پرونده
1. ثبت درخواست و صدور شناسه عمومی/کد رهگیری تصادفی.
2. تعیین نوع خدمت، سطح محرمانگی، سازمان مقصد و زمان ثبت.
3. ارجاع به صف سازمان و تعیین مسئول مجاز.
4. ثبت هر اقدام به‌صورت رویداد جدید؛ تاریخچه قبلی حذف یا بازنویسی نمی‌شود.
5. درخواست اطلاعات تکمیلی از شهروند در صورت نیاز.
6. ثبت نتیجه و دلیل بستن پرونده؛ امکان بازگشایی با ثبت دلیل.
7. اعلام وضعیت به شهروند از صفحه پیگیری و در صورت رضایت، پیامک/اعلان.

وضعیت‌های مشترک پیشنهادی: `received`, `triaged`, `assigned`, `in_progress`, `waiting_for_citizen`, `waiting_for_agency`, `resolved`, `closed`, `rejected`. متن فارسی هر وضعیت باید در رابط کاربری نمایش داده شود. تغییر وضعیت فقط برای نقش‌های مجاز مجاز است.

## قرارداد API پیشنهادی (هنوز فعال نیست)
- `POST /api/v1/integrations/v1/cases` — ایجاد پرونده از سوی سازمان/سامانه مجاز؛ با `Idempotency-Key` برای جلوگیری از ثبت تکراری.
- `GET /api/v1/integrations/v1/cases/{caseId}` — مشاهده پرونده‌های مجاز همان سازمان.
- `POST /api/v1/integrations/v1/cases/{caseId}/events` — ثبت اقدام یا تغییر وضعیت با توضیح و شناسه کارمند.
- `GET /api/v1/integrations/v1/cases/{caseId}/events` — تاریخچه مجاز پرونده.
- `POST /api/v1/integrations/v1/webhooks/test` — آزمایش مقصد webhook.
- پاسخ ایجاد پرونده باید شامل `caseId`, `trackingCode`, `status`, `createdAt` باشد.

نمونه درخواست مفهومی:
```json
{
  "externalReference": "شناسه پرونده در سامانه اداره",
  "serviceType": "urban_issue",
  "subject": "شرح کوتاه و غیرمحرمانه",
  "description": "توضیحات لازم",
  "citizenConsent": true
}
```
نمونه بالا قرارداد پیشنهادی است و تا زمان ساخت endpoint، قابل فراخوانی نیست. اطلاعات هویتی یا اسناد حساس نباید در عنوان، URL، لاگ یا webhook عمومی ارسال شوند.

## امنیت و حاکمیت
- هر سازمان یک شناسه و فضای داده مجزا دارد؛ سازمانی حق مشاهده پرونده سازمان دیگر را ندارد.
- نقش‌ها حداقلی باشند: سازمان‌مدیر، مسئول پرونده، کارشناس، بازرس فقط‌خواندنی.
- ورود امن، MFA برای مدیران، ابطال فوری کلید، محدودسازی نرخ، اعتبارسنجی ورودی و ثبت رخداد امنیتی لازم است.
- گزارش عمومی فقط کد رهگیری تصادفی و وضعیت/پیام‌های از پیش تعریف‌شده را نشان دهد؛ اطلاعات تماس، متن محرمانه، اسناد و نام کارمند نمایش داده نشود.
- لاگ حسابرسی شامل زمان، عامل، عملیات، نتیجه و شناسه پرونده باشد؛ اسرار و اطلاعات حساس در لاگ ذخیره نشود.
- انتقال داده باید حداقلی و بر اساس توافق رسمی و مجوز قانونی باشد. اتصال فنی به‌تنهایی به معنی همکاری رسمی یا اختیار قانونی اداره نیست.
- پیامک تنها پس از انتخاب ارائه‌دهنده، رضایت کاربر، تنظیم اسرار در محیط سرور و آزمون تحویل فعال شود.

## مسیر اجرایی امن
1. تکمیل و آزمون رهگیری سفارش فعلی بدون دست‌زدن به داده‌های تولید.
2. تعریف مدل مشترک پرونده/رویداد و مهاجرت سازگار با داده‌های قبلی.
3. ساخت ورود سازمانی، جداسازی داده‌ها و پنل ساده کارشناس؛ پیش از API عمومی.
4. ساخت API با تست‌های دسترسی بین‌سازمانی، تکرار درخواست، ورودی نامعتبر و نرخ بالا.
5. افزودن webhook امضاشده، retry و مانیتورینگ.
6. آزمایش با یک سازمان پایلوت که رسماً رضایت داده است؛ سپس گسترش مرحله‌ای.
7. پس از گذراندن آزمون‌ها و تأیید انسانی، انتشار نسخه تولید.

## معیار آماده‌بودن
- یک اداره نمی‌تواند پرونده اداره دیگر را بخواند یا تغییر دهد.
- ارسال دوباره درخواست با همان کلید idempotency پرونده تکراری نمی‌سازد.
- همه تغییرات وضعیت در تاریخچه باقی می‌مانند.
- کد رهگیری بدون افشای اطلاعات شخصی کار می‌کند.
- کلید قابل ابطال است و در کد منبع یا مرورگر دیده نمی‌شود.
- خطاهای webhook قابل مشاهده و قابل تکرارند.
- برای پرونده بسته‌شده، نتیجه و دلیل ثبت شده است.
